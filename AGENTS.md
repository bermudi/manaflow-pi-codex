# AGENTS.md — @bermudi/pi-codex

Codex-native apply_patch, web search, and remote compaction for pi.

## Pi extension import contract (hard-won)

Pi loads extensions through a sandbox; this is the ONLY reliable mental model:

- **Bundled pi** (dist/bundle, the default download): jiti + `virtualModules`
  maps a fixed id list to bundled modules. Unmapped ids resolve natively.
- **Unbundled pi** (npm global install of dist/cli.js): jiti + `alias` table
  that **prefix-rewrites** `@earendil-works/pi-ai*` (and friends) onto
  `dist/compat.js`, corrupting any subpath import of those packages.
- **Pi's package installer runs npm with `--legacy-peer-deps`** —
  peerDependencies are NEVER on disk in `~/.pi/agent/npm`. This is how 0.1.5
  broke in production.
- **pi >= 0.87.1 warns when host-provided packages appear in
  `dependencies`** of an extension package (its resource-loader keeps a
  HOST_PROVIDED_EXTENSION_PACKAGES list: pi-ai, pi-coding-agent, pi-tui,
  pi-agent-core, typebox, @sinclair/typebox). Their docs say to declare them
  in `peerDependencies` with a `"*"` range and include anything else you
  need in the published tarball.

Consequences:

1. Import sandbox-served ids statically (root, `/compat`, `/oauth`,
   `/providers/all`, typebox, pi-coding-agent, pi-tui, pi-agent-core).
   `generateDiffString` and `CompactionSummaryMessageComponent` are public
   root exports of pi-coding-agent — never reach into pi's dist tree by URL.
2. pi-ai's `./api/*` subpath (the Responses converters) is public API but NOT
   sandbox-served, and pi-ai can no longer be a regular dependency (see
   above). The subpath module is therefore **vendored**:
   `src/vendor/openai-responses-shared.mjs` is generated by
   `scripts/vendor-pi-ai.mjs` (`npm run vendor`) as a fully self-contained
   bundle — pi-ai's relative imports AND its runtime dep `partial-json` are
   inlined, so nothing resolves at runtime. The converter consumes plain
   data (no instanceof checks), so running a private copy alongside pi's
   sandboxed pi-ai is safe. **Vendor from the pi-ai that the installed
   `@earendil-works/pi-coding-agent` depends on (its nested copy), not the
   root-hoisted pi-ai** — other devDependencies can move the root to a newer
   version than the one pi actually bundles (this happened with pi-ai 1.3.0
   nested vs 1.4.0 hoisted). After moving the pi-coding-agent devDependency,
   run `npm run vendor` and commit; `test/vendor-parity.test.ts` resolves the
   same nested copy, checks the vendored banner version against it, and
   fails when conversions drift (fixtures cover cross-model fc_/ctc_ id
   dropping, whitespace-only/empty tool output, additional_tools, and
   grammar/strict tool conversion).
3. `test/import-contract.test.ts` enforces all of this statically (plus the
   host-provided/dependencies rule mirroring pi's resource-loader). It would
   have caught the 0.1.5 regression. Keep it passing; extend SANDBOXED_IDS
   when pi's loader changes.

## Verification

Before shipping a resolution change, verify all three runtimes:

- `npm test` (plain node + the RPC load test = alias mode via devDep pi)
- Managed-root simulation: install the packed tarball into a fake
  `~/.pi/agent/npm` with `npm install --omit=dev --legacy-peer-deps`, write
  `settings.json` with `"npm:@bermudi/pi-codex"`, run the REAL bundled pi:
  `HOME=<fake> pi --mode rpc --no-session --no-skills --no-context-files
  --offline <<< '{"id":"state","type":"get_state"}'` → expect success.

## Release

Releasing is a **tag push**, not a local `npm publish`:

1. `npm version <patch|minor> --no-git-tag-version`, commit as `0.1.<N>`, tag `v0.1.<N>`, push both.
2. `.github/workflows/publish-manaflow-pi-codex.yml` fires on `v*` tags:
   verifies tag ↔ package version, runs check + tests, then publishes via
   npm trusted publishing (OIDC, `environment: npm-publish`) with provenance.
3. There is deliberately no npm token on this machine — a local
   `npm publish` fails with 404. That is expected, not a blocker. Check the
   result with `gh run list --workflow publish-manaflow-pi-codex.yml`.
4. Scoped-package tarball URLs drop the scope:
   `@bermudi/pi-codex` → `.../-/pi-codex-<version>.tgz` (not
   `bermudi-pi-codex-<version>.tgz`).
5. **Only bermudi installs new versions.** Publishing ends the agent's job:
   never run `pi update`, `pi install`, or otherwise modify the real managed
   root (`~/.pi/agent/npm`). Report the published version and stop — he
   installs when he chooses. The fake-HOME managed-root *simulation* in
   Verification is unaffected.
6. **`npm view` lags the publish; the registry does not.** Right after a tag
   run the local packument cache can still report `latest` = previous version,
   or E404 the new one, while the package is already live — `npm pack
   @bermudi/pi-codex@<new>` succeeds in the same breath. Do not call a publish
   failed on that. Confirm against the registry itself
   (`curl -sS https://registry.npmjs.org/@bermudi%2Fpi-codex | jq '.["dist-tags"]'`)
   and re-query with `--prefer-online`. Verify `dist.gitHead` equals the release
   commit, then install the *published* tarball into a fake HOME and boot it —
   the published artifact, not the local `npm pack`, is the thing users get.

## Server compaction capture

Pi's cache warmer replays a request with `maxTokens: 1` and the original
`onPayload`/`onProviderStreamEvent` callbacks while a foreground response may
still be streaming. Capture must be keyed by `response.completed.response.id`
and committed from `turn_end` only when it matches the assistant message's
`responseId`; a request hook invocation is not evidence of a foreground
request. Do not attach response usage to the resulting compaction entry (the
assistant message already carries it), and do not commit a checkpoint for a
truncated (`stopReason: "length"`) response before pi's recoverable-length
recovery runs.

## Tool visibility (Pi 1.4.0)

The recorded `toolsAdded` list proves Pi declared a tool locally, not that the
serving backend exposed it to the model. A model's "list your tools" answer is
not a registry query either. Test actual calls. On the plain `openai` Responses
CLI connection, a live comparison with the same custom SYSTEM.md showed
`input[].additional_tools` could be accepted without usable tool visibility;
moving the exact schemas to top-level `tools` restored a native apply_patch call.
`src/responses-tools.ts` performs that request-boundary compatibility repair.
Keep Codex's working incremental transport unchanged, preserve wire schemas,
and filter removed tools rather than reviving historical declarations.

A custom SYSTEM.md also replaces Pi's generated tools/rules sections, so
`promptGuidelines` may never reach the model. Essential patch-tool guidance
belongs in its description as well. Do not infer active tools from the static
inventory in a custom prompt, or rewrite the operator's config as a workaround.

## Conventions

- Node ≥ 22.19, ESM, TypeScript strict (`npm run check`).
- Tests: `node --test --experimental-strip-types` (npm test).
- `pi install <tarball-path>` is a LOCAL path install (loads from the path,
  no managed npm root) — not a fidelity test for npm installs.
- Long-term: if pi ever serves `./api/*` through the sandbox, drop the
  vendored file + `npm run vendor` and import the subpath statically.
